# Мультиклиповая модель проекта

> План перехода от «проект = одна запись» к «проект = последовательность клипов».
> Составлен 2026-09-14 по итогам сплошного прохода по коду. Все ссылки на файлы — на состояние `main` от этой даты.

## Зачем

Мультиклип нужен ради **пересъёма**, а не ради монтажа.

Записал четыре минуты демо, на третьей оговорился — сегодня выбор: переснимать всё целиком либо экспортировать и клеить во внешнем редакторе. Для инструмента, которым делают демо продукта, это не «не хватает фичи», а дыра в основном рабочем процессе: вероятность ошибки на длинном дубле высокая, а цена ошибки — весь дубль.

Всё остальное, что обычно называют мультиклипом, у нас либо уже есть, либо запланировано без него:

| Что просят | Нужен ли мультиклип |
|---|---|
| Резать дорожку | **Нет.** `TrimRegion` вырезает куски, работает. Автоудаление тишины ([UPGRADES #3](../UPGRADES.md)) — то же самое автоматически |
| Вставлять картинки | **Нет.** `AnnotationRegion` с `type: "image"` работает. Картинка во весь кадр — это клип-карточка, см. этап 2 |
| Переходы на стыках вырезок | **Нет.** [UPGRADES #4](../UPGRADES.md), внутри одной записи. Там же сказано: это 80% ценности переходов за 20% стоимости |
| Переходы между записями | **Да**, но это оставшиеся 20% ценности |
| Пересъём куска | **Да. Ради этого всё и делается** |
| Интро/аутро, титульные карточки | **Да**, в лёгком виде (клип без видеоисточника) |

### Граница, которую нельзя переходить

- **Секвенция** — клипы подряд, один видеоряд, один звукоряд, стык за стыком. Это починка рабочего процесса. Делаем.
- **Многодорожечность** — слои, B-roll поверх A-roll, независимые аудиодорожки, композитинг. Это монтажка. **Не делаем.**

Ценность продукта в автоматическом полише, которого в монтажке нет: зум по клику, сглаживание курсора, обои, клик-риппл. В универсальном монтаже с бесплатным DaVinci не соревнуются. Подтверждение — собственный роадмап: в топ-10 и топ-7 камеры **семнадцать фич, и ни одна не требует мультиклипа**. Упоминаний у него там ровно два, и оба — про его отсутствие: #4 отмечает, что переходы между клипами без него невозможны, а #10 заранее спроектирован обходным путём «поверх одноклиповой модели».

## Ключевое решение: регионы остаются в source-времени

Это главное проектное решение, и от него зависит стоимость всего остального.

**Регионы (зумы, тримы, скорости, аннотации, блюры) продолжают адресовать время своей записи, как сейчас.** Клип владеет своими регионами. Время таймлайна вычисляется поверх, а не хранится.

Альтернатива — перевести регионы в время таймлайна — выглядит проще ровно один день. Потом выясняется, что любое перемещение клипа, изменение его трима или скорости обязано переписать координаты всех регионов во всех последующих клипах. Это источник багов, которые не ловятся тестами, и потеря инварианта, который у нас уже есть и уже проверен.

Следствие, ради которого всё и затевается: **весь существующий код регионов, вся математика `computeTimeline`, весь MCP-контракт и весь экспортный рендер продолжают работать без изменений — но per-clip.** Меняется только слой, который раскладывает клипы по одной оси.

## Модель данных

```ts
interface Clip {
  id: string;
  media: ProjectMedia | null;   // null = клип-карточка (картинка/цвет)
  sourceDurationMs: number;     // длительность записи, не выхода
  editor: ClipEditorState;      // регионы + покадровые настройки, в source-времени
}

interface Sequence {
  clips: Clip[];                // порядок = порядок воспроизведения
}
```

Две оси времени:

- `sourceMs` — внутри записи клипа. Это то, что видят регионы, телеметрия курсора, транскрипт, `get_frame`. **Не меняется.**
- `timelineMs` — позиция в выходной последовательности.

Отображение строится одной чистой функцией поверх существующей [`computeTimeline`](../../src/lib/mcp/timeline.ts):

```
computeSequence(clips) -> Array<{
  clipId, outStartMs, outEndMs,        // место клипа на оси таймлайна
  segments: KeepSegment[]              // его keep-сегменты в source-времени
}>
```

Накопительное смещение: каждый клип получает `outStartMs` = сумме выходных длительностей предыдущих. `timelineMs → (clipId, sourceMs)` — поиск клипа по диапазону плюс проход по его сегментам. Обратное — так же.

Часть настроек глобальна для проекта, а не для клипа: обои, паддинг, скругление, тень, соотношение сторон, формат экспорта. Их место — `Sequence`, а не `Clip`, иначе стык клипов станет стыком фонов. Курсорные и вебкам-настройки — спорно, см. открытые вопросы.

## Аудит по коду

### Блокеры — без этого пересъём невозможен

**1. Запись уничтожает редактор.** Это главное открытие прохода и самое дорогое ограничение.

Причина — не в записи, а в модели окон. `mainWindow` в [`main.ts`](../../electron/main.ts) — это **один слот**, в котором лежит либо HUD-оверлей, либо редактор: `createWindow()` создаёт туда `createHudOverlayWindow()`, `createEditorWindowWrapper()` закрывает то, что было, и кладёт туда редактор, `switchToHudWrapper()` делает обратное через `mainWindow.close(); mainWindow = null`. Различаются они только по URL — `isEditorWindow()` смотрит на `windowType=editor`.

Поэтому уход в рекордер физически уничтожает окно редактора: рендерер умирает, и вся React-стейт вместе с ним — `EditorState`, история undo, загруженное видео. Никакого сохранения и восстановления сегодня нет вообще (поиск по `autosave`/`restoreEditor` пуст).

Отдельно стоит отметить: причина закрытия в коде нигде не записана. Логика «одного слота» объясняет механику, но не намерение — возможно, редактор закрывают ещё и чтобы он не попал в захват. Проверять это предположение придётся отдельно, и от ответа зависит осуществимость варианта (B).

Значит, «записать ещё один дубль и добавить его в открытый проект» упирается не в таймлайн, а в жизненный цикл окон. Два пути:

- **(A) Сохранить и восстановить.** Перед уходом в рекордер проект пишется на диск, после записи открывается обратно, новый клип дописывается в конец. Главное достоинство — **модель окон не трогается вообще**: один слот остаётся одним слотом. Переиспользует готовое: сохранение/загрузку проекта, `editorHasUnsavedChanges`, `getApprovedProjectSession`. И ложится на уже построенную защиту MCP-тула `start_recording`, который сегодня отказывает при несохранённых изменениях — с (A) отказ превращается в «сначала сохраню, потом запишу».
- **(B) Прятать, а не закрывать.** `mainWindow.hide()` вместо `close()`. Звучит дешевле, но требует разломать один слот на два отдельно отслеживаемых окна, а живой рендерер остаётся во время захвата: WebGL-контекст Pixi, декодер видео и превью конкурируют за GPU ровно с пайплайном записи. Для экранного рекордера это плохой размен.

**Выбор: (A).** Дороже по коду, но не трогает модель окон, тестируемо и не ставит живой WebGL рядом с захватом.

**Разведка вперёд плана.** Это самый рискованный неизвестный во всём документе, а работой он приезжает только на этапе 6. Поэтому в плане есть **этап 0**: прогнать цикл «сохранить проект → уйти в запись → вернуться → открыть проект обратно» вручную на живом приложении, до всякого кода.

### Результат этапа 0 (2026-09-14)

**Цикл работает.** Проект с зумом, вырезкой и сменёнными обоями сохранён, после него сделаны ещё две записи, проект открыт обратно — вернулся целиком. Записи копятся в `RECORDINGS_DIR` рядом, ничего не затирается. Вариант (A) жив, этапы 3–6 остаются в силе как расписаны.

Проверка опровергла одно утверждение аудита и нашла один настоящий баг.

**Опровергнуто: путь из редактора в рекордер есть.** Выше было сказано, что его нет. Это неверно — в шапке редактора есть кнопка «Вернуться к записи», просто зовёт она не `switchToHud`, а `startNewRecording()`, и уже хендлер `start-new-recording` в [`handlers.ts`](../../electron/ipc/handlers.ts) дёргает `_switchToHud()`. Поиск по имени функции её не нашёл. Для плана это хорошая новость: у пересъёма есть готовое место в UI, новую кнопку изобретать не нужно.

**Баг на этом же пути: несохранённая работа уничтожается молча.** `handleNewRecordingConfirm` в [`VideoEditor.tsx`](../../src/components/video-editor/VideoEditor.tsx) вызывает `startNewRecording()` без единой проверки, а `switchToHudWrapper` выставляет `isForceClosing = true` перед `close()` — и обработчик закрытия начинается с `if (isForceClosing || ...) return`, то есть гард несохранённых изменений обходится целиком. Диалог перед кнопкой при этом сообщает «Ваша текущая сессия была сохранена»: про видеофайл это правда, про правки — нет.

Это баг сегодняшнего дня, не мультиклипа. Но чинить его придётся в любом случае: пересъём на этапе 6 пойдёт ровно по этой кнопке, и первое, что от неё потребуется, — перестать терять работу.

**2. Сессия записи — глобальный синглтон в main.** `currentRecordingSession` в [`handlers.ts:358`](../../electron/ipc/handlers.ts) — одна на приложение, её перетирает каждая новая запись. Для «дописать клип» нужен явный режим: результат записи не заменяет текущую сессию, а возвращается вызывающему для присоединения.

**3. Модель доверия к путям.** [`getApprovedProjectSession`](../../electron/ipc/handlers.ts) одобряет чтение media только внутри `RECORDINGS_DIR` или папки проекта — защита от проектного файла, который подсовывает произвольные пути. С N клипами правило обобщается на каждый клип, но забыть нельзя: проектный файл с полусотней клипов, ведущих куда угодно, не должен получать одобрение оптом.

### Хорошие новости — тут работы меньше, чем казалось

**4. Экспорт уже отвязан от источника.** В кадровом цикле [`videoExporter.ts`](../../src/lib/exporter/videoExporter.ts) выходной таймстемп — это `frameIndex * frameDuration`, монотонный счётчик; `_exportTimestampUs`, который отдаёт декодер, **игнорируется**. Значит, последовательный прогон N декодеров в один энкодер ложится естественно: счётчик просто продолжает расти через границу клипа.

**5. `computeTimeline` — готовая точка расширения.** Чистая функция без состояния, единственный источник истины, экспортный декодер уже делегирует сюда ([`streamingDecoder.buildSegments`](../../src/lib/exporter/streamingDecoder.ts)). Секвенция — это вызвать её по клипу и склеить со смещениями. Пишется и тестируется за день.

**6. Таймлайн-UI не предполагает, что ms — это время источника.** Он работает как окно `Range {start, end}` над `totalMs` с зумом и панорамой ([`TimelineEditor.tsx`](../../src/components/video-editor/timeline/TimelineEditor.tsx)). Ряды уже абстрагированы (`Row` для зумов, тримов, аннотаций, блюров, скоростей), полоса клипов встаёт туда структурно. Менять придётся не рендеринг рядов, а drag-операции: они обязаны переводить `timelineMs → (clip, sourceMs)`.

**7. Рендерер не требует пересоздания между клипами.** [`FrameRenderer`](../../src/lib/exporter/frameRenderer.ts) берёт конфиг в конструкторе, но выходной размер кадра между клипами не меняется, а `updateLayout()` читает `this.config.videoWidth` покадрово. Достаточно метода `setClipContext()`, меняющего per-clip поля (регионы, размеры источника, телеметрию курсора) без повторного `initialize()` и без пересоздания Pixi.

**8. Телеметрия курсора уже ключуется путём.** `useCursorTelemetry(videoPath)` — обобщается до «по клипу» прямолинейно.

### Средние — учесть в дизайне

**9. Разные разрешения клипов.** Записал 4K-монитор, потом окно 1080p — нужна политика вписывания и per-clip размеры источника. Механически решается пунктом 7, но политику («вписать по длинной стороне», «кропнуть», «чёрные поля») надо выбрать явно.

**10. Пружина зума — непрерывное состояние.** `zoomSpringState` в рендерере копится между кадрами. На стыке клипов её надо сбрасывать, иначе зум «перетечёт» через склейку. То же касается состояния motion blur курсора.

**11. Source-copy fast path.** [`getSourceCopyFastPathBlockers`](../../src/lib/exporter/videoExporter.ts) получает ещё одну причину отказа: клипов больше одного. Забыть — значит получить экспорт, который молча отдаёт первый клип целиком.

**12. MCP-контракт становится ложным.** У нас везде написано «все таймстемпы — на часах исходной записи». С N записями это неверно. Нужен `clipId` в `get_project`, `apply_commands`, `get_frame`, `get_transcript`, `export_walkthrough`. Хорошая новость: слой построен за `computeTimeline` и `buildProjectSummary`, поэтому адаптируется, а не сопротивляется.

### Главная ловушка: аудио

Вынесено отдельно, потому что это единственное место, которое при беглом чтении кода выглядит вдвое дешевле, чем оказывается.

В [`AudioProcessor.process`](../../src/lib/exporter/audioEncoder.ts) **два разных пути**:

- **Только тримы:** демукс → декод → пропустить пакеты внутри тримов → переэнкодить со сдвигом таймстемпов. Быстро, оффлайн, частота дискретизации берётся из конфига источника.
- **Есть регионы скорости:** `renderPitchPreservedTimelineAudio` — проигрывает `<audio>` с `playbackRate` **в реальном времени** и пишет результат через `MediaRecorder`. Так сделано ради сохранения питча: `playbackRate` у медиа-элемента питч держит, а `AudioBufferSourceNode.playbackRate` в оффлайн-контексте — нет.

Последствия для мультиклипа:
1. Разные записи — разные частоты дискретизации и число каналов. Склеивать закодированные потоки нельзя, нужен общий знаменатель.
2. Реал-тайм путь на N клипах — это N реал-тайм проходов. Пять клипов по минуте = пять минут только на звук.

**Обход:** ввести один общий сборщик PCM. Для каждого клипа получить его звук как PCM на общей частоте (48 кГц) — существующим быстрым путём, если скоростей нет, и существующим реал-тайм путём, если есть, — сложить встык в один буфер, закодировать один раз. Существующий `muxRenderedAudioBlob` уже реализует шаблон «отрендерили звук в блоб → демукс → мукс», так что точка стыковки есть.

Реал-тайм цена остаётся, но платится только за клипы, где реально есть ускорение, и она честно показывается в прогрессе. Настоящее решение — питч-сохраняющий тайм-стретч (WSOLA) в оффлайн-контексте — это самостоятельный DSP-проект, и **в этот план он не входит**.

## Обход сложностей: клип-карточка как пробный шар

Прежде чем брать второй видеодекодер и склейку звука, стоит сделать **клип без видеоисточника** — титульную карточку, интро/аутро, статичную картинку на N секунд.

Это [UPGRADES #10](../UPGRADES.md), и там она описана как «концепция *сцены до/после записи* **поверх одноклиповой модели**» — то есть как обходной путь, придуманный именно потому, что секвенции нет. С секвенцией карточка перестаёт быть костылём и становится обычным клипом. Фича при этом сохраняет собственную ценность, а заодно **прогоняет всю модель секвенции насквозь**, обходя обе опасные части:

- двухуровневое время — работает;
- полоса клипов на таймлайне — работает;
- экспортный цикл по клипам со сквозным счётчиком кадров — работает;
- превью с переключением между клипами — работает, но без смены видео-текстуры (карточка рисуется как картинка);
- **звук** — карточка молчит, но в выходном треке обязана быть тишина нужной длины. Это простейший возможный случай задачи «склеить PCM из разных источников»: скелет конкатенации строится на источнике, который не может сломаться.

То есть карточка даёт готовый и проверенный каркас, в который потом добавляются рискованные части — по одной, на работающем основании.

| **6** | Проект переживает запись: сохранение перед уходом в рекордер, возврат и дописывание клипа. Опирается на существующую кнопку «Вернуться к записи», которой сначала надо перестать терять несохранённое | **Ради этого всё делалось.** Пересъём работает |
| **7** | MCP: `clipId` по всему контракту, обновление документации тулов | Агент снова видит проект целиком, а не первый клип |
| **8** | Переходы между клипами | Дешевеют: два одновременно живых источника — то, что требует переход, — появились на этапе 5 |

Этап 0 идёт первым и стоит полвечера. Этапы 1 и 2 самодостаточны и безопасны. Этап 6 — цель; этапы 3–5 существуют, чтобы он был возможен. Этап 8 делать только после того, как [UPGRADES #4](../UPGRADES.md) (переходы на стыках тримов) закроет бо́льшую часть той же боли дешевле.

### Результат этапа 1 (2026-09-14)

Сделано: [`src/lib/sequence.ts`](../../src/lib/sequence.ts) — вторая ось времени и перевод между ней и временем записи; формат проекта v4 с миграцией с v1, v2 и v3; разделение состояния через `CLIP_EDITOR_KEYS`; общий на два процесса разбор медиа `projectMediaList`.

**Чего в этапе не оказалось.** План говорил «весь код переведён на секвенцию», и это подразумевало объём, которого нет. Сплошной поиск по рендереру нашёл ровно **двух** потребителей timeline-математики: экспортный декодер (`streamingDecoder.buildSegments`) и `buildProjectSummary`. Всё остальное — плейхед, таймлайн-UI, превью — работает с сырой длительностью источника и до секвенции просто не дотягивается.

Переведён `buildProjectSummary`: он отвечает агенту, и его ответ про выжившие сегменты и длину выхода с появлением второго клипа станет вопросом к секвенции, а не к одной записи. Существующие тесты прошли без правок — это и есть доказательство, что при одном клипе ответ побайтово тот же.

Экспортный декодер **сознательно не тронут**: обернуть `computeTimeline` в `computeSequence` с одним клипом — чистая церемония, которая ничего не меняет, но трогает самый нагруженный путь. Он станет клипоориентированным на этапе 3, когда у него появится по декодеру на клип.

## Что сознательно не делаем

- **Многодорожечность** — слои, B-roll, композитинг. См. границу в начале документа.
- **Питч-сохраняющий тайм-стретч (WSOLA)** — самостоятельный DSP-проект. Реал-тайм путь для клипов со скоростью остаётся, цена документируется.
- **Перекрытие клипов на таймлайне** — только встык. Перекрытие нужно переходам, но там оно локальное и решается на этапе 8, а не общей моделью.
- **Раздельные аудиодорожки на клип** — громкость и фейды per-clip можно добавить позже поверх сборщика PCM из этапа 4; в модель это не закладывается.

### Результат этапа 2 (2026-09-14)

Карточку можно создать, назвать, задать длительность, переставить и удалить; она сохраняется в проект и попадает в экспорт MP4 и GIF.

**Порядок вместо оси.** Полоса клипов сознательно **не** легла на ось таймлайна: ось — это время записи, а карточка лежит вне его. Свести их на одну линейку — это работа этапа 5, и до неё полоса показывает порядок (что про карточку и есть главное), а таймлайн под ней продолжает показывать время записи. Следствие, которое надо знать: **прокрутить плейхедом сквозь карточку нельзя.** Видно, как она выглядит, — в панели рисуется тем же кодом, что и в экспорте.

**Чего у карточки нет намеренно.** Своего фона (берётся near-black приложения), картинки, второй строки. Всё это дописывается полем в модель без смены версии формата — и лучше делать это, когда станет понятно из использования, а не заранее.

**Три бага поймано по дороге, все до пользователя.** Звук уезжал вперёд на длину интро-карточки (см. «Известные пробелы»). `handleExport` использовал список карточек, не объявив его в зависимостях, — экспорт мог уйти со старым составом; мемо пришлось поднять выше по файлу, иначе зависимость нельзя было добавить. И первая версия обработчика «добавить карточку» вычисляла id новой карточки отдельно от вставки — два вызова `nextCardId` могли разойтись; теперь список строится один раз, а id читается из него.

**Аудио-путь экспортёра теперь исполняется в тестах.** До 2026-09-14 в `tests/fixtures/sample.webm` не было аудиодорожки вообще (только V_VP9), поэтому весь звук экспорта — выбор кодека, ремап таймстемпов под тримы, реал-тайм путь для скоростей — не исполнялся ни одним тестом. Добавлена фикстура `sample-with-audio.webm` (VP9 + Opus, 48 кГц, синус 440 Гц, 2 с), и на ней проверяется синхронизация с интро-карточкой: первые 0.8 с должны быть тишиной, а после 1.2 с — тон. Проверено, что тест **ловит** баг: со снятым сдвигом пик в первой секунде 0.129 вместо тишины.

## Открытые вопросы

1. ~~**Курсорные и вебкам-настройки — глобальные или per-clip?**~~ **Решено 2026-09-14, формат v4.** Per-clip уходит ровно то, что адресует запись: `cropRegion`, `zoomRegions`, `trimRegions`, `speedRegions`, `annotationRegions` (блюры — это аннотации). Всё остальное общее: обои, паддинг, скругление, тень, соотношение сторон, весь вид курсора, все настройки вебкамеры, настройки экспорта. Список зафиксирован константой `CLIP_EDITOR_KEYS`, и тест требует, чтобы разделение не теряло и не дублировало ни одного ключа. Спорными остаются два: `cropRegion` отдан клипу (разные источники — разное кадрирование), а `webcamLayoutPreset` оставлен общим, хотя у клипа без вебкамеры он мог бы быть свой; оба дёшево передвинуть позже.
2. **Что делать с проектом при пересъёме, если клипы записаны с разным соотношением сторон.** Отказывать, вписывать или предлагать кроп — решать на этапе 6, когда будет видно реальное поведение.
3. **Транскрипт и субтитры через границу клипов.** Whisper работает по одному файлу. Караоке-субтитры ([UPGRADES #2](../UPGRADES.md)) поверх мультиклипа — это N транскриптов со сдвигом в время таймлайна. Не блокер, но развилка.
