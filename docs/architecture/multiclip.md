# Мультиклиповая модель проекта

> План перехода от «проект = одна запись» к «проект = последовательность клипов».
> Составлен 2026-09-14 по итогам сплошного прохода по коду. Все ссылки на файлы — на состояние `main` от этой даты.

## Зачем

Мультиклип нужен ради **пересъёма**, а не ради монтажа.

Записал четыре минуты демо, на третьей оговорился — сегодня выбор: переснимать всё целиком либо экспортировать и клеить во внешнем редакторе. Для инструмента, которым делают демо продукта, это не «не хватает фичи», а дыра в основном рабочем процессе: вероятность ошибки на длинном дубле высокая, а цена ошибки — весь дубль.

Всё остальное, что обычно называют мультиклипом, у нас либо уже есть, либо запланировано без него:

| Что просят | Нужен ли мультиклип |
|---|---|
| Резать дорожку | **Нет.** `TrimRegion` вырезает куски, работает. Автоудаление тишины ([UPGRADES #3](../UPGRADES.md)) — то же самое автоматически |
| Вставлять картинки | **Нет.** `AnnotationRegion` с `type: "image"` работает. Картинка во весь кадр — это клип-карточка, см. этап 2 |
| Переходы на стыках вырезок | **Нет.** [UPGRADES #4](../UPGRADES.md), внутри одной записи. Там же сказано: это 80% ценности переходов за 20% стоимости |
| Переходы между записями | **Да**, но это оставшиеся 20% ценности |
| Пересъём куска | **Да. Ради этого всё и делается** |
| Интро/аутро, титульные карточки | **Да**, в лёгком виде (клип без видеоисточника) |

### Граница, которую нельзя переходить

- **Секвенция** — клипы подряд, один видеоряд, один звукоряд, стык за стыком. Это починка рабочего процесса. Делаем.
- **Многодорожечность** — слои, B-roll поверх A-roll, независимые аудиодорожки, композитинг. Это монтажка. **Не делаем.**

Ценность продукта в автоматическом полише, которого в монтажке нет: зум по клику, сглаживание курсора, обои, клик-риппл. В универсальном монтаже с бесплатным DaVinci не соревнуются. Подтверждение — собственный роадмап: в топ-10 и топ-7 камеры **семнадцать фич, и ни одна не требует мультиклипа**. Упоминаний у него там ровно два, и оба — про его отсутствие: #4 отмечает, что переходы между клипами без него невозможны, а #10 заранее спроектирован обходным путём «поверх одноклиповой модели».

## Ключевое решение: регионы остаются в source-времени

Это главное проектное решение, и от него зависит стоимость всего остального.

**Регионы (зумы, тримы, скорости, аннотации, блюры) продолжают адресовать время своей записи, как сейчас.** Клип владеет своими регионами. Время таймлайна вычисляется поверх, а не хранится.

Альтернатива — перевести регионы в время таймлайна — выглядит проще ровно один день. Потом выясняется, что любое перемещение клипа, изменение его трима или скорости обязано переписать координаты всех регионов во всех последующих клипах. Это источник багов, которые не ловятся тестами, и потеря инварианта, который у нас уже есть и уже проверен.

Следствие, ради которого всё и затевается: **весь существующий код регионов, вся математика `computeTimeline`, весь MCP-контракт и весь экспортный рендер продолжают работать без изменений — но per-clip.** Меняется только слой, который раскладывает клипы по одной оси.

## Модель данных

```ts
interface Clip {
  id: string;
  media: ProjectMedia | null;   // null = клип-карточка (картинка/цвет)
  sourceDurationMs: number;     // длительность записи, не выхода
  editor: ClipEditorState;      // регионы + покадровые настройки, в source-времени
}

interface Sequence {
  clips: Clip[];                // порядок = порядок воспроизведения
}
```

Две оси времени:

- `sourceMs` — внутри записи клипа. Это то, что видят регионы, телеметрия курсора, транскрипт, `get_frame`. **Не меняется.**
- `timelineMs` — позиция в выходной последовательности.

Отображение строится одной чистой функцией поверх существующей [`computeTimeline`](../../src/lib/mcp/timeline.ts):

```
computeSequence(clips) -> Array<{
  clipId, outStartMs, outEndMs,        // место клипа на оси таймлайна
  segments: KeepSegment[]              // его keep-сегменты в source-времени
}>
```

Накопительное смещение: каждый клип получает `outStartMs` = сумме выходных длительностей предыдущих. `timelineMs → (clipId, sourceMs)` — поиск клипа по диапазону плюс проход по его сегментам. Обратное — так же.

Часть настроек глобальна для проекта, а не для клипа: обои, паддинг, скругление, тень, соотношение сторон, формат экспорта. Их место — `Sequence`, а не `Clip`, иначе стык клипов станет стыком фонов. Курсорные и вебкам-настройки — спорно, см. открытые вопросы.

## Аудит по коду

### Блокеры — без этого пересъём невозможен

**1. Запись уничтожает редактор.** Это главное открытие прохода и самое дорогое ограничение.

Причина — не в записи, а в модели окон. `mainWindow` в [`main.ts`](../../electron/main.ts) — это **один слот**, в котором лежит либо HUD-оверлей, либо редактор: `createWindow()` создаёт туда `createHudOverlayWindow()`, `createEditorWindowWrapper()` закрывает то, что было, и кладёт туда редактор, `switchToHudWrapper()` делает обратное через `mainWindow.close(); mainWindow = null`. Различаются они только по URL — `isEditorWindow()` смотрит на `windowType=editor`.

Поэтому уход в рекордер физически уничтожает окно редактора: рендерер умирает, и вся React-стейт вместе с ним — `EditorState`, история undo, загруженное видео. Никакого сохранения и восстановления сегодня нет вообще (поиск по `autosave`/`restoreEditor` пуст).

Отдельно стоит отметить: причина закрытия в коде нигде не записана. Логика «одного слота» объясняет механику, но не намерение — возможно, редактор закрывают ещё и чтобы он не попал в захват. Проверять это предположение придётся отдельно, и от ответа зависит осуществимость варианта (B).

Значит, «записать ещё один дубль и добавить его в открытый проект» упирается не в таймлайн, а в жизненный цикл окон. Два пути:

- **(A) Сохранить и восстановить.** Перед уходом в рекордер проект пишется на диск, после записи открывается обратно, новый клип дописывается в конец. Главное достоинство — **модель окон не трогается вообще**: один слот остаётся одним слотом. Переиспользует готовое: сохранение/загрузку проекта, `editorHasUnsavedChanges`, `getApprovedProjectSession`. И ложится на уже построенную защиту MCP-тула `start_recording`, который сегодня отказывает при несохранённых изменениях — с (A) отказ превращается в «сначала сохраню, потом запишу».
- **(B) Прятать, а не закрывать.** `mainWindow.hide()` вместо `close()`. Звучит дешевле, но требует разломать один слот на два отдельно отслеживаемых окна, а живой рендерер остаётся во время захвата: WebGL-контекст Pixi, декодер видео и превью конкурируют за GPU ровно с пайплайном записи. Для экранного рекордера это плохой размен.

**Выбор: (A).** Дороже по коду, но не трогает модель окон, тестируемо и не ставит живой WebGL рядом с захватом.

**Разведка вперёд плана.** Это самый рискованный неизвестный во всём документе, а работой он приезжает только на этапе 7 (в исходной нумерации — 6). Поэтому в плане есть **этап 0**: прогнать цикл «сохранить проект → уйти в запись → вернуться → открыть проект обратно» вручную на живом приложении, до всякого кода.

### Результат этапа 0 (2026-09-14)

**Цикл работает.** Проект с зумом, вырезкой и сменёнными обоями сохранён, после него сделаны ещё две записи, проект открыт обратно — вернулся целиком. Записи копятся в `RECORDINGS_DIR` рядом, ничего не затирается. Вариант (A) жив, этапы 3–6 остаются в силе как расписаны.

Проверка опровергла одно утверждение аудита и нашла один настоящий баг.

**Опровергнуто: путь из редактора в рекордер есть.** Выше было сказано, что его нет. Это неверно — в шапке редактора есть кнопка «Вернуться к записи», просто зовёт она не `switchToHud`, а `startNewRecording()`, и уже хендлер `start-new-recording` в [`handlers.ts`](../../electron/ipc/handlers.ts) дёргает `_switchToHud()`. Поиск по имени функции её не нашёл. Для плана это хорошая новость: у пересъёма есть готовое место в UI, новую кнопку изобретать не нужно.

**Баг на этом же пути: несохранённая работа уничтожается молча.** `handleNewRecordingConfirm` в [`VideoEditor.tsx`](../../src/components/video-editor/VideoEditor.tsx) вызывает `startNewRecording()` без единой проверки, а `switchToHudWrapper` выставляет `isForceClosing = true` перед `close()` — и обработчик закрытия начинается с `if (isForceClosing || ...) return`, то есть гард несохранённых изменений обходится целиком. Диалог перед кнопкой при этом сообщает «Ваша текущая сессия была сохранена»: про видеофайл это правда, про правки — нет.

Это баг сегодняшнего дня, не мультиклипа. Но чинить его придётся в любом случае: пересъём на этапе 7 пойдёт ровно по этой кнопке, и первое, что от неё потребуется, — перестать терять работу. *Дополнение от 2026-09-16: на этапе 7 гард снят — не ослаблен, а стал не нужен: работа больше не теряется, потому что проект откладывается перед уходом.*

**2. Сессия записи — глобальный синглтон в main.** `currentRecordingSession` в [`handlers.ts:358`](../../electron/ipc/handlers.ts) — одна на приложение, её перетирает каждая новая запись. Для «дописать клип» нужен явный режим: результат записи не заменяет текущую сессию, а возвращается вызывающему для присоединения.

**3. Модель доверия к путям.** [`getApprovedProjectSession`](../../electron/ipc/handlers.ts) одобряет чтение media только внутри `RECORDINGS_DIR` или папки проекта — защита от проектного файла, который подсовывает произвольные пути. С N клипами правило обобщается на каждый клип, но забыть нельзя: проектный файл с полусотней клипов, ведущих куда угодно, не должен получать одобрение оптом.

### Хорошие новости — тут работы меньше, чем казалось

**4. Экспорт уже отвязан от источника.** В кадровом цикле [`videoExporter.ts`](../../src/lib/exporter/videoExporter.ts) выходной таймстемп — это `frameIndex * frameDuration`, монотонный счётчик; `_exportTimestampUs`, который отдаёт декодер, **игнорируется**. Значит, последовательный прогон N декодеров в один энкодер ложится естественно: счётчик просто продолжает расти через границу клипа.

**5. `computeTimeline` — готовая точка расширения.** Чистая функция без состояния, единственный источник истины, экспортный декодер уже делегирует сюда ([`streamingDecoder.buildSegments`](../../src/lib/exporter/streamingDecoder.ts)). Секвенция — это вызвать её по клипу и склеить со смещениями. Пишется и тестируется за день.

**6. Таймлайн-UI не предполагает, что ms — это время источника.** Он работает как окно `Range {start, end}` над `totalMs` с зумом и панорамой ([`TimelineEditor.tsx`](../../src/components/video-editor/timeline/TimelineEditor.tsx)). Ряды уже абстрагированы (`Row` для зумов, тримов, аннотаций, блюров, скоростей), полоса клипов встаёт туда структурно. Менять придётся не рендеринг рядов, а drag-операции: они обязаны переводить `timelineMs → (clip, sourceMs)`.

**7. Рендерер не требует пересоздания между клипами.** [`FrameRenderer`](../../src/lib/exporter/frameRenderer.ts) берёт конфиг в конструкторе, но выходной размер кадра между клипами не меняется, а `updateLayout()` читает `this.config.videoWidth` покадрово. Достаточно метода `setClipContext()`, меняющего per-clip поля (регионы, размеры источника, телеметрию курсора) без повторного `initialize()` и без пересоздания Pixi.

**8. Телеметрия курсора уже ключуется путём.** `useCursorTelemetry(videoPath)` — обобщается до «по клипу» прямолинейно.

### Средние — учесть в дизайне

**9. Разные разрешения клипов.** Записал 4K-монитор, потом окно 1080p — нужна политика вписывания и per-clip размеры источника. Механически решается пунктом 7, но политику («вписать по длинной стороне», «кропнуть», «чёрные поля») надо выбрать явно.

**10. Пружина зума — непрерывное состояние.** `zoomSpringState` в рендерере копится между кадрами. На стыке клипов её надо сбрасывать, иначе зум «перетечёт» через склейку. То же касается состояния motion blur курсора.

**11. Source-copy fast path.** [`getSourceCopyFastPathBlockers`](../../src/lib/exporter/videoExporter.ts) получает ещё одну причину отказа: клипов больше одного. Забыть — значит получить экспорт, который молча отдаёт первый клип целиком.

**12. MCP-контракт становится ложным.** У нас везде написано «все таймстемпы — на часах исходной записи». С N записями это неверно. Нужен `clipId` в `get_project`, `apply_commands`, `get_frame`, `get_transcript`, `export_walkthrough`. Хорошая новость: слой построен за `computeTimeline` и `buildProjectSummary`, поэтому адаптируется, а не сопротивляется.

### Главная ловушка: аудио

Вынесено отдельно, потому что это единственное место, которое при беглом чтении кода выглядит вдвое дешевле, чем оказывается.

В [`AudioProcessor.process`](../../src/lib/exporter/audioEncoder.ts) **два разных пути**:

- **Только тримы:** демукс → декод → пропустить пакеты внутри тримов → переэнкодить со сдвигом таймстемпов. Быстро, оффлайн, частота дискретизации берётся из конфига источника.
- **Есть регионы скорости:** `renderPitchPreservedTimelineAudio` — проигрывает `<audio>` с `playbackRate` **в реальном времени** и пишет результат через `MediaRecorder`. Так сделано ради сохранения питча: `playbackRate` у медиа-элемента питч держит, а `AudioBufferSourceNode.playbackRate` в оффлайн-контексте — нет.

Последствия для мультиклипа:
1. Разные записи — разные частоты дискретизации и число каналов. Склеивать закодированные потоки нельзя, нужен общий знаменатель.
2. Реал-тайм путь на N клипах — это N реал-тайм проходов. Пять клипов по минуте = пять минут только на звук.

**Обход:** ввести один общий сборщик PCM. Для каждого клипа получить его звук как PCM на общей частоте (48 кГц) — существующим быстрым путём, если скоростей нет, и существующим реал-тайм путём, если есть, — сложить встык в один буфер, закодировать один раз. Существующий `muxRenderedAudioBlob` уже реализует шаблон «отрендерили звук в блоб → демукс → мукс», так что точка стыковки есть.

Реал-тайм цена остаётся, но платится только за клипы, где реально есть ускорение, и она честно показывается в прогрессе. Настоящее решение — питч-сохраняющий тайм-стретч (WSOLA) в оффлайн-контексте — это самостоятельный DSP-проект, и **в этот план он не входит**.

## Обход сложностей: клип-карточка как пробный шар

Прежде чем брать второй видеодекодер и склейку звука, стоит сделать **клип без видеоисточника** — титульную карточку, интро/аутро, статичную картинку на N секунд.

Это [UPGRADES #10](../UPGRADES.md), и там она описана как «концепция *сцены до/после записи* **поверх одноклиповой модели**» — то есть как обходной путь, придуманный именно потому, что секвенции нет. С секвенцией карточка перестаёт быть костылём и становится обычным клипом. Фича при этом сохраняет собственную ценность, а заодно **прогоняет всю модель секвенции насквозь**, обходя обе опасные части:

- двухуровневое время — работает;
- полоса клипов на таймлайне — работает;
- экспортный цикл по клипам со сквозным счётчиком кадров — работает;
- превью с переключением между клипами — работает, но без смены видео-текстуры (карточка рисуется как картинка);
- **звук** — карточка молчит, но в выходном треке обязана быть тишина нужной длины. Это простейший возможный случай задачи «склеить PCM из разных источников»: скелет конкатенации строится на источнике, который не может сломаться.

То есть карточка даёт готовый и проверенный каркас, в который потом добавляются рискованные части — по одной, на работающем основании.

### Сверка перед этапом 6 (2026-09-15)

Исходная строка плана — «по видео-элементу на клип, предзагрузка следующего, смена `videoSprite.texture` на границе» — описывала механику и молчала про главное. Проход по [`VideoPlayback.tsx`](../../src/components/video-editor/VideoPlayback.tsx) и его месту в редакторе дал шесть поправок.

**1. Что показывает таймлайн — решено: вариант A.** Таймлайн остаётся таймлайном активной записи, и правки делаются только там. Секвенция смотрится в отдельном режиме **только для просмотра**: воспроизведение и перемотка по всей длине, сквозь карточки и стыки записей. Отвергнутый вариант B — таймлайн всей секвенции с правкой регионов любого клипа на месте — требует общей истории отмены на все записи, отменяет решение «переключение начинает историю заново» из этапа 5 и пересчитывает координаты регионов на лету. Это шаг к монтажке, от которой план отказался в самом начале. Следствие для аудита: пункт 6 («drag-операции таймлайна обязаны переводить `timelineMs → (clip, sourceMs)`») при варианте A не нужен вовсе.

**2. Встраивать секвенцию в плеер редактора нельзя — нужен второй экземпляр.** Плеер редактора несущий: экспорт берёт размеры источника из его видео-элемента, горячие клавиши и шаг по кадрам двигают именно его, MCP-экспорт идёт через него. И он пишет в состояние активной записи: `onDurationChange` → длительность таймлайна, `onTimeUpdate` → плейхед, перетаскивание фокуса зума и аннотаций → правки. Прогнать через него чужой клип значит испортить длительность и плейхед активной записи. Поэтому просмотр — отдельный компонент поверх превью, со своим экземпляром плеера и своим временем; плеер редактора под ним остаётся смонтированным и на паузе. Два WebGL-контекста одновременно — далеко от лимита, а пересоздание плеера на стыке контексты не копит: `Application.destroy` у Pixi сам вызывает `loseContext()` (проверено по исходнику `GlContextSystem`).

**3. Смена записи на стыке — пересоздание плеера, а не смена текстуры.** Плеер уже пересоздаётся по ключу `videoPath` при переключении записи, и все его внутренние состояния (зафиксированные размеры, пружина, размытие, курсор) рассчитаны на это. Смена текстуры внутри живого плеера потребовала бы сбрасывать их руками — ровно та работа, что в экспорте заняла восемь состояний. На стыке будет короткий скачок; план это допускает. Два одновременно живых источника по-настоящему нужны только плавному переходу — это работа этапа 9, туда и переезжает.

**4. Длительности неактивных записей рендереру неизвестны вообще.** Секвенции нужна исходная длина каждой записи, а в проекте её нет: экспорт узнаёт её из демуксера на первой фазе, превью — только у открытой записи. Нужен зонд метаданных. Записи самого приложения получают длительность в заголовке при остановке (`electron/recording/webm-duration.ts`), импорт — обычные файлы с заголовком, так что зонд почти всегда отвечает сразу; для остального есть обходной путь с перемоткой в конец, который уже применяет плеер.

**5. Данные для просмотра уже собирает экспорт.** `buildExportSequence` строит ровно тот список, что нужен просмотру: карточки, у каждой записи медиа, регионы, кроп, данные курсора с той же проверкой «не рисовать второй курсор». Он становится общим построителем, а загрузка данных курсора неактивных записей кэшируется по пути файла — просмотр пересобирает список при каждой правке активной записи, и перечитывать файлы курсора каждый раз незачем.

**6. Кадр просмотра = кадр экспорта, включая его причуду.** При соотношении «как у источника» экспорт секвенции берёт размер кадра у **активной** записи, то есть размер выходного файла зависит от того, какая запись сейчас открыта. Это недосмотр этапа 4, не этапа 6. Просмотр обязан показывать то, что выйдет в файл, поэтому повторяет это поведение; исправление (кадр по первой записи) — отдельной правкой, одновременно в экспорте и просмотре.

**Уточнённый объём этапа 6:**

- чистая логика продвижения по секвенции (`src/lib/sequencePlayback.ts`): куда перейти, когда запись дошла до конца своих выживших сегментов, упёрлась в хвостовой трим или карточка отыграла своё — с юнит-тестами;
- зонд длительностей записей;
- общий построитель списка клипов для экспорта и просмотра, с кэшем данных курсора;
- компонент просмотра: плеер текущей записи или карточка тем же `drawCardFrame`, полоса секвенции с плейхедом и перемоткой, пуск/пауза, пробел;
- кнопка входа в полосе клипов и выход обратно к правке;
- переводы на все 13 языков;
- e2e на настоящем приложении: проект «карточка + две записи», воспроизведение проходит карточку и доходит до второй записи, перемотка в карточку показывает карточку.

**Чего в этапе нет:** плавного стыка, правки из режима просмотра, звука карточек (они и в экспорте молчат), общего кадра по первой записи (пункт 6).

### Результат этапа 1 (2026-09-14)

Сделано: [`src/lib/sequence.ts`](../../src/lib/sequence.ts) — вторая ось времени и перевод между ней и временем записи; формат проекта v4 с миграцией с v1, v2 и v3; разделение состояния через `CLIP_EDITOR_KEYS`; общий на два процесса разбор медиа `projectMediaList`.

**Чего в этапе не оказалось.** План говорил «весь код переведён на секвенцию», и это подразумевало объём, которого нет. Сплошной поиск по рендереру нашёл ровно **двух** потребителей timeline-математики: экспортный декодер (`streamingDecoder.buildSegments`) и `buildProjectSummary`. Всё остальное — плейхед, таймлайн-UI, превью — работает с сырой длительностью источника и до секвенции просто не дотягивается.

Переведён `buildProjectSummary`: он отвечает агенту, и его ответ про выжившие сегменты и длину выхода с появлением второго клипа станет вопросом к секвенции, а не к одной записи. Существующие тесты прошли без правок — это и есть доказательство, что при одном клипе ответ побайтово тот же.

Экспортный декодер **сознательно не тронут**: обернуть `computeTimeline` в `computeSequence` с одним клипом — чистая церемония, которая ничего не меняет, но трогает самый нагруженный путь. Он станет клипоориентированным на этапе 3, когда у него появится по декодеру на клип.

## Что сознательно не делаем

- **Многодорожечность** — слои, B-roll, композитинг. См. границу в начале документа.
- **Питч-сохраняющий тайм-стретч (WSOLA)** — самостоятельный DSP-проект. Реал-тайм путь для клипов со скоростью остаётся, цена документируется.
- **Перекрытие клипов на таймлайне** — только встык. Перекрытие нужно переходам, но там оно локальное и решается на этапе 9, а не общей моделью.
- **Раздельные аудиодорожки на клип** — громкость и фейды per-clip можно добавить позже поверх сборщика PCM из этапа 4; в модель это не закладывается.

Карточку можно создать, назвать, задать длительность, переставить и удалить; она сохраняется в проект и попадает в экспорт MP4 и GIF.

**Порядок вместо оси.** Полоса клипов сознательно **не** легла на ось таймлайна: ось — это время записи, а карточка лежит вне его. ### Этап 3 (бывшие 3 и 4): почему это одна работа

Разделять их нельзя. Экспорт, где видео собрано из всех записей, а звук взят только из первой, — это ровно то «молчаливо отдаём меньше, чем в проекте», что уже дважды признано неприемлемым (карточки в GIF, source-copy fast path). Значит, видеоцикл по клипам и склейка звука отгружаются вместе.

Начато с рискованной половины — звука, потому что её можно строить и проверять отдельно от видеоцикла, а видеоцикл без неё отгрузить всё равно нельзя.

**Как устроена склейка.** Закодированный звук разных записей просто встык не кладётся: дубли различаются кодеком, частотой дискретизации и числом каналов. Поэтому каждый клип приводится к сэмплам на общей частоте, кладётся в один буфер по своему смещению, и этот буфер кодируется один раз. Тишина под карточкой и в разрывах получается сама собой — буфер изначально нулевой.

**Скорость обходится, а не решается.** Питч сохраняет только реал-таймовый проход через медиа-элемент; копирование сэмплов его сдвинет. Поэтому клип со скоростями приходит в сборщик **уже отрендеренным** — как готовые сэмплы, к которым нечего применять. `applyTrimsToSamples` на сегмент со скоростью не тихо ресемплит, а бросает исключение с внятным текстом: молчаливый сдвиг тона нашли бы не скоро.

### Этап 7: сделано (2026-09-16)

Кнопка «Вернуться к записи» стала пересъёмом. Уходя в рекордер, редактор откладывает проект; записанный дубль возвращается в тот же проект последним клипом и открывается для правки, а прежний дубль остаётся на месте со своими зумами, вырезками и аннотациями. Диалог перед уходом больше ничего не выясняет — он сообщает, что следующий дубль будет добавлен в этот проект.

**Где рвалась связь.** В одной строке главного процесса: `set-current-recording-session` обнулял путь проекта, и новый редактор открывал одну свежую запись. Теперь рядом живёт «ожидание пересъёма» — только в памяти, снимается при использовании, при открытии другого проекта и при «Новом проекте», и не переживает перезапуск.

**Проект откладывается не в файл пользователя.** Служебная копия пишется в `userData/retake-pending.openscreen`: молча дописывать в файл пользователя неправильно, а у самого частого пересъёма — записал, не понравилось, переснял — файла ещё и нет вовсе. Если проект уже сохранён и на нём нет правок, не откладывается ничего: файл на диске и так всё говорит. Копия удаляется сразу после использования и при каждом старте приложения.

**Куда сохраняется после возврата.** Туда же, куда сохранялся раньше: путь проекта восстанавливается вместе с ним. Если пути не было, `Ctrl+S` по-прежнему спросит, куда сохранять. Проект после пересъёма честно считается несохранённым — в файле на диске нового дубля нет.

**Путь агента.** MCP-тул `start_recording` отказывает при несохранённых правках, то есть доходит до записи только с актуальным файлом на диске: там достаточно запомнить путь, и это сделано. Полный контракт с `clipId` — этап 8.

**Проверки.**
- Юнит-тесты `checkoutNewRecording`: новый дубль встаёт в конец, становится активным и пустым, прежний забирает свои медиа и правки, карточки не двигаются, id не переиспользуются.
- E2E «несохранённый проект» (`retake.spec.ts`): запись, зум через MCP, уход в рекордер, проверка, что проект отложен на диск, затем тот же обмен сообщениями, который делает рекордер по окончании записи, и возврат. Проверено: в проекте две записи, активна новая и она без правок, зум первой записи на месте после переключения, служебная копия удалена. Проверено, что тест падает, если проект не откладывать.
- E2E «сохранённый проект»: ничего не откладывается, а сохранение после пересъёма пишет обе записи в тот же файл и **не** спрашивает куда (системный диалог подменён счётчиком). Проверено, что тест падает, если не восстанавливать путь проекта.
- Тест-гард «уход в рекордер спрашивает про несохранённые правки» из этапа 0 убран: он охранял потерю, которой больше нет. На его месте стоит более сильное утверждение — работа возвращается.

### Сверка перед этапом 8 (2026-09-16)

Пункт 12 аудита требовал `clipId` «по всему контракту». Проход по коду показал, что контракт делится на две части с разной ценой, и валить их в одну — ошибка.

**1. Чего агент сейчас не видит и во что это обходится.** `buildProjectSummary` строит секвенцию из **одного** клипа с фиксированным `SINGLE_CLIP_ID` и отдаёт `output.durationMs` по нему. В проекте с карточкой и двумя дублями агент получает длину одной записи и ни слова о том, что есть другие. Он не ошибается в мелочи — он уверенно отвечает про чужой проект: предлагает вырезать «последние секунды», которых в выходном файле нет и близко.

**2. Читать чужой клип дёшево, править — дорого.** Читающие тулы работают от пути файла: `get_frame` и `get_transcript` получают URL, `get_audio_profile` декодирует по URL, телеметрия неактивных записей уже читается с кэшем (этап 6). Длительность чужой записи тоже теперь известна — зондом из этапа 6. А вот правка идёт через `applyCommands` над плоским состоянием редактора и историю отмены, которая принадлежит **открытой** записи. Писать в чужой клип мимо этого — это вторая копия правил валидации и правки, которых не видно на экране.

**3. Поэтому правка остаётся на открытой записи, а переключение становится явным тулом.** `open_clip` делает ровно то, что клик по клипу в полосе: открывает запись и начинает историю отмены заново. Это честно и совпадает с тем, что видит пользователь: агент правит то же, что открыто на экране. Альтернатива — `clipId` в `apply_commands` — потребовала бы либо переносить правки через `clips[].editor` в обход истории (правка, которую нельзя отменить), либо втихую переключать запись под руками пользователя.

**4. Две оси времени должны быть названы прямо, иначе всё остальное бессмысленно.** Сегодня `timeDomain` обещает «все таймстемпы — часы исходной записи», и для одной записи это правда. В секвенции у каждого клипа свои часы, а у готового видео — свои. Поэтому в ответе появляются обе: у каждого клипа своё место на оси таймлайна (`outStartMs`/`outEndMs`), а регионы и команды остаются в часах своей записи. Это то же решение, что принято в начале документа, просто сказанное агенту вслух.

**5. Что остаётся ложью и после этапа.** `export_walkthrough` берёт кадры только из открытой записи: шаги на чужих клипах — это другой тул с другой ценой (кадр из каждого клипа), и он ждёт спроса. `get_cursor_events` и `get_audio_profile` с `clipId` дают данные чужой записи, но их идея — «подскажи, где кликали» — про открытую. Всё это должно быть написано в описаниях тулов, а не оставлено агенту на догадку.

**Уточнённый объём этапа 8:**

- `get_project` отдаёт `sequence`: клипы по порядку с id, видом (запись или карточка), длиной, местом на оси таймлайна и пометкой открытого; `output.durationMs` — длина всего видео, а не одной записи;
- длины неактивных записей — зондом из этапа 6, с честным ответом, если длина ещё не известна;
- `clipId` в `get_frame`, `get_transcript`, `get_audio_profile`, `get_cursor_events`; по умолчанию — открытая запись;
- новый тул `open_clip` (только в режиме полного доступа, как и правка);
- описания тулов и `timeDomain` переписаны под две оси;
- юнит-тесты на сводку проекта с секвенцией и на разрешение `clipId`;
- e2e: агент видит обе записи и карточку, берёт кадр из неактивной записи, переключается на неё и правит.

**Чего в этапе нет:** правки чужого клипа без переключения, шагов walkthrough по нескольким клипам, `clipId` в `export_video` (экспорт всегда собирает весь проект).

### Сверка перед этапом 7 (2026-09-16)

Ключевая развилка варианта (A) — «сохранить и восстановить» — оказалась не там, где её ждал аудит. Окно редактора действительно уничтожается, но сложность не в этом, а в **одной строке главного процесса**, и в том, чего у пользователя в этот момент может не быть — сохранённого файла проекта.

**1. Место, где рвётся связь с проектом, — ровно одно.** После остановки записи рендерер зовёт `set-current-recording-session`, и этот обработчик делает `currentProjectPath = null`. Дальше новый редактор при монтировании спрашивает сперва «есть ли текущий проект» (`load-current-project-file`), не находит его и открывает одну свежую запись. Всё остальное по пути — `start-new-recording` → `_switchToHud()` → уничтожение окна — состояния проекта не трогает вовсе. Значит, пересъём — это не «восстановить редактор», а «не потерять указатель на проект и дописать в него клип».

**2. Сохранение молча писать в файл пользователя нельзя, а сохранённого файла может и не быть.** Самый обычный случай пересъёма — записал дубль, сразу не понравилось, переснял: проект при этом **никогда не сохранялся**, пути у него нет, и терять первый дубль нельзя. Поэтому перед уходом проект откладывается в служебный файл в `userData` (один и тот же путь, удаляется при использовании и при старте приложения), а **не** дописывается в файл пользователя. Если у проекта уже есть путь, он запоминается отдельно: при возврате правки продолжают считаться несохранёнными, и `Ctrl+S` пишет туда же, куда писал раньше. Медиа при этом лежат в папке записей, так что модель доверия на служебный файл распространяется без исключений.

**3. Когда файл проекта на диске и так свеж, откладывать нечего.** Если у проекта есть путь и нет несохранённых правок, достаточно запомнить путь. Это же делает путь агента: MCP-тул `start_recording` сегодня отказывает при несохранённых правках, а при сохранённых после починки просто продолжит проект вместо того, чтобы его бросить.

**4. Ожидание пересъёма живёт только в памяти главного процесса.** Оно ставится при уходе и снимается при использовании, при загрузке другого проекта, при «Новом проекте» и при перезапуске приложения. Иначе забытое ожидание однажды приклеило бы новую запись к позавчерашнему проекту. Служебный файл при этом чистится при старте: память о нём не переживает перезапуск, а сам он пережил бы.

**5. Диалог «Вернуться к записи» меняет смысл, и это упрощение.** Сегодня кнопка означает «уйти и записать заново», её текст обещает «сессия сохранена», а гард несохранённых изменений, добавленный на этапе 0, спрашивает, что делать с правками. После этапа 7 она означает «дописать ещё один дубль в этот проект», ничего не теряет и потому не спрашивает; «начать с нуля» остаётся отдельной кнопкой «Новый проект», после которой запись открывает пустой проект, как и раньше.

**6. Новая запись становится активной и встаёт в конец.** Пересняли — значит с этим дублем и работать. Вставка на место старого дубля отдельной операцией не делается: переставить и удалить уже умеет полоса клипов (этап 5). Следствие, которое надо знать: при соотношении «как у источника» кадр экспорта берётся у активной записи, так что после пересъёма форма кадра — это форма нового дубля (причуда из сверки перед этапом 6, пункт 6).

**Уточнённый объём этапа 7:**

- откладывание проекта и память об ожидании в главном процессе, со снятием на всех путях выхода;
- дописывание клипа при возврате: редактор при монтировании спрашивает про ожидание раньше, чем про текущий проект;
- упрощение кнопки «Вернуться к записи» и её текста, на все 13 языков;
- юнит-тесты на чистую часть (что именно откладывать и как дописывать);
- e2e: настоящий цикл «редактор с проектом → уход в рекордер → появление новой записи → редактор» без захвата экрана — завершение записи в тесте изображается тем же IPC, который зовёт рекордер.

**Чего в этапе нет:** захвата экрана в тестах (его нет ни у одного e2e), замены дубля на месте, пересъёма из агента дальше пункта 3.

### Этап 6: сделано (2026-09-15)

### Этап 5: сделано (2026-09-15)

В полосе клипов появились «Добавить видео», переключение записи кликом и удаление неактивной записи. Секвенцию из нескольких записей теперь можно собрать руками, без написания файла проекта.

**Существующий импорт видео пришлось не переиспользовать, а обойти** — по двум причинам, найденным в коде до начала работы. Во-первых, `open-video-file-picker` обнуляет `currentProjectPath` в главном процессе, а сохранение на место доверяет ровно этому пути: после добавления клипа `Ctrl+S` превратился бы в «Сохранить как». Во-вторых, он не копирует файл, а разрешает путь только в памяти процесса — проект, ссылающийся на видео из «Загрузок», сохранился бы, а после перезапуска отказался бы открываться, потому что при загрузке доверяются только папка записей и папка проекта. Поэтому новый обработчик `pick-video-clip` не трогает путь проекта и копирует файл извне в папку записей (`planClipImport`, с `COPYFILE_EXCL`); файл, уже лежащий там, используется на месте.

**Переключение начинает историю отмены заново.** Видео живёт вне истории; отмена, дотянувшаяся за момент переключения, наложила бы правки прошлой записи на видео нынешней. То же самое уже делает открытие проекта. Подсказка на кнопке переключения об этом говорит.

**Переключение не делает проект изменённым** — и это проверено, а не предположено: каждая запись пишется в файл одинаково, какая бы из них ни была активной, так что снимок проекта после переключения побайтово совпадает с исходным (юнит-тест).

**Удаление.** Удалить можно только неактивную запись и никогда — последнюю: активная оставила бы на экране видео, которое ничему не принадлежит, последняя опустошила бы проект.

**E2E на настоящем приложении** (`add-video-clip.spec.ts`): системный диалог выбора подменён в главном процессе, выбранное видео лежит вне папки записей. Проверено, что копия появилась и совпадает с оригиналом побайтово, проект стал изменённым, экспорт содержит обе записи со звуком на своих местах, а зум первой записи не утекает во вторую при переключении и возвращается при переключении обратно. Проверено, что тест падает, если при уходе с записи терять её зумы.

### Этап 4: сделано (2026-09-15)

**Сверка снова переоценила цену.** Там сказано, что около 100 обращений к единственной записи в `VideoEditor` придётся перенести в клип. На деле их **не пришлось трогать**: около 50 мест только *читают* состояние записи, и они продолжают означать «активная запись». *Пишут* его пять мест, и ни одно менять не пришлось — все они уже работают с редактором в начальном состоянии. Тот же приём, что с регионами в этапе 2, сработал второй раз.

**Устройство.** У проекта есть активная запись (`activeClipId`). Её медиа и правки живут там же, где всегда жили у единственной записи: в загруженном видео редактора и в плоских полях. Каждая другая запись хранит `media` и `editor` у себя в клипе. У активного клипа нет ни того, ни другого, и это инвариант, который держит нормализация: две копии рано или поздно разошлись бы. `activeClipId` не сохраняется — проект всегда открывается на первой записи.

**Экспорт.** При двух и более записях редактор собирает секвенцию и отдаёт экспортёру; при одной — прежнюю форму конфига, потому что только её принимает source-copy fast path. Данные курсора неактивной записи подгружаются в момент экспорта. Оверлей курсора решается **для каждой записи отдельно** по тем же правилам, что у активной (`hasEditableCursorOverlay`): дубль, где системный курсор уже зашит в картинку, не получает второй курсор поверх.

**Проверено, что старое состояние не протечёт в новую запись.** Сессия записи и путь видео подхватываются только при монтировании нового окна редактора, а оно пересоздаётся при каждом переходе; импорт видео доступен только в пустом редакторе, то есть после «Нового проекта», который сбрасывает состояние. Ни один путь загрузки записи не встречает список клипов от прошлого проекта.

**E2E на настоящем Electron** (`sequence-export.spec.ts`): проект из немой записи 4:3, карточки и записи с тоном грузится в редактор, экспортируется через MCP, звук готового файла декодируется — тишина первые 2.8 с, тон после 3.3 с, длина ~5 с. Проверено, что тест падает, если редактор не отдаёт секвенцию: в экспорт уходит одна немая запись, и звуковой дорожки нет вовсе.

### Этап 3, видеополовина: сделано (2026-09-15)

Оба экспортёра рендерят секвенцию: `sequence` в конфиге — упорядоченный список записей и карточек. Без него классическая одна запись с `cards` вокруг описывается той же секвенцией, так что старые вызовы идут тем же путём. Секвенция живёт в отдельном модуле `exportSequence.ts`, чтобы GIF-экспортёр не тянул в рантайме MP4-экспортёр ради одной функции.

Устройство: сначала открываются все записи (длины нужны до первого кадра — для бюджета прогресса и смещений звука), потом клипы рендерятся по порядку, у каждой записи свой декодер и свой вебкам-декодер, потом звук по всем. Рендерер один на весь экспорт; между записями меняются только 10 клиповых полей через `setClipContext()`.

**Что на самом деле опасно на стыке — проверено по коду, а не предположено.** Пружина зума сама сбрасывается при скачке времени назад или больше 80 мс (`dtMs <= 0 || dtMs > 80`), а у следующей записи время источника начинается снова около нуля — так что зум через обычную склейку не протекает, и тест «зум в конце первого клипа» ничего бы не доказал. Протекает другое: размытие движения меряет, насколько камера сдвинулась с прошлого кадра, и первый кадр новой записи сравнивался бы с последним кадром старой — всплеск размытия; авто-фокус плыл бы от курсора старой записи к курсору новой. Сбрасываются все восемь. Раскладка (`layoutCache`) пересчитывается на каждом кадре из текущих размеров, так что устаревшей раскладки не бывает.

**Fast path для секвенции запрещён явно.** При явной `sequence` поля верхнего уровня пусты, и проверка «есть ли правки» по ним назвала бы отредактированную секвенцию нетронутой и скопировала бы первый файл как есть.

**Тест, который сначала ничего не доказывал.** Проверка «вторая запись вписана по своим размерам» сравнивает пиксели этого клипа в секвенции и в одиночку. Первая версия фикстуры была 320×240 — то же соотношение 4:3, что у 640×480, а спрайт растягивается под заданный размер, поэтому устаревшие размеры давали ту же картинку: тест прошёл **с отключённой сменой контекста**. Фикстура переделана в 320×180 (16:9); теперь без смены контекста разница 61 при пороге 8. Для звука то же: обнулённые смещения роняют оба теста.

**Формат звука секвенции.** Задаёт первая запись со звуком, остальные ресэмплируются к ней. Если записей больше одной, каналы ограничены стерео: у объёмного дубля рядом с моно нет разумной раскладки шире.

### Этап 3, звуковая половина: сделано (2026-09-15)

Старый аудио-путь экспорта (`process` → `processTrimOnlyAudio` / `muxRenderedAudioBlob`) заменён целиком на `AudioProcessor.processSequence`: каждый клип приводится к сэмплам на частоте экспорта и кладётся на общую дорожку по смещению своей картинки. Одиночная запись с карточками — частный случай, поэтому временная «подкладка тишины» из этапа 2 удалена за ненадобностью.

Что изменилось в поведении и почему:

- **Звук привязан к кадрам, а не к миллисекундам.** Смещение клипа считается из числа кадров перед ним. Картинка квантуется кадрами; если считать звук точно по миллисекундам, на каждом стыке набегало бы до кадра расхождения.
- **Тримы стали сэмпл-точными.** Раньше пропускались целые пакеты в регионе трима (~20 мс шага), теперь режутся сэмплы.
- **Разрывы в потоке сохраняются.** Декодированные куски раскладываются по своим таймстемпам, а не встык: иначе после подвисшего микрофона всё последующее съехало бы раньше картинки. Куски в пределах двух сэмплов от ожидаемого места «прилипают», чтобы округление таймстемпов не давало щелчков. Этой регрессии не видел ни один тест — фикстуры без разрывов, — она поймана чтением собственного кода до коммита.
- **Многоканальный звук сводится, а не обрезается.** Лишние каналы не выбрасываются (в 5.1 речь живёт в центральном), а смешиваются существующим `downmixPlanarChannelsForExport`.

**Путь с регионами скорости никогда не проверялся — и выяснилось, где он работает.** Ни один тест ни в какой среде ни разу не экспортировал с регионом скорости. В headless-браузере тестов реал-тайм проход зависает навсегда на `audioContext.resume()`: контекст остаётся `suspended` даже с флагом автоплея. На старом коде — ровно так же, так что это не регрессия. В настоящем Electron путь работает: новый e2e `speed-audio-export.spec.ts` экспортирует запись со звуком на 2× и декодирует звук готового файла в рендерере — ~1 с тона. Проверено, что тест падает, если реал-тайм путь не отдаёт звук.

## Открытые вопросы

1. ~~**Курсорные и вебкам-настройки — глобальные или per-clip?**~~ **Решено 2026-09-14, формат v4.** Per-clip уходит ровно то, что адресует запись: `cropRegion`, `zoomRegions`, `trimRegions`, `speedRegions`, `annotationRegions` (блюры — это аннотации). Всё остальное общее: обои, паддинг, скругление, тень, соотношение сторон, весь вид курсора, все настройки вебкамеры, настройки экспорта. Список зафиксирован константой `CLIP_EDITOR_KEYS`, и тест требует, чтобы разделение не теряло и не дублировало ни одного ключа. Спорными остаются два: `cropRegion` отдан клипу (разные источники — разное кадрирование), а `webcamLayoutPreset` оставлен общим, хотя у клипа без вебкамеры он мог бы быть свой; оба дёшево передвинуть позже.
2. **Что делать с проектом при пересъёме, если клипы записаны с разным соотношением сторон.** Частично решено: экспорт вписывает каждую запись в общий кадр по её собственным размерам (этап 3), и просмотр секвенции обязан показывать то же самое. Открытым остаётся, *чей* это кадр при соотношении «как у источника» — см. сверку перед этапом 6, пункт 6.
3. **Транскрипт и субтитры через границу клипов.** Whisper работает по одному файлу. Караоке-субтитры ([UPGRADES #2](../UPGRADES.md)) поверх мультиклипа — это N транскриптов со сдвигом в время таймлайна. Не блокер, но развилка.
